# f-board Technical Decisions

이 문서는 2026년 8~9월 리팩터링과 기능 보완 과정에서 확정한 공개 가능한 기술 결정을 정리한다.

## 1. 공통 컴포넌트는 역할과 상태 경계를 기준으로 분리한다

- **배경:** 페이지마다 버튼, 입력 요소, 로딩·빈 상태·에러 표현이 개별 스타일로 작성되어 수정 범위와 표현 방식이 달랐다.
- **결정:** 반복 횟수만 보지 않고 독립적인 역할, 반복 가능성, 상태 경계를 기준으로 공통화한다.
- **적용:** 버튼, 입력 요소, 상태 화면, 확인 모달, 추천 헤더를 공통 컴포넌트로 분리하고 게시글 카드, 댓글, 마이페이지 아코디언은 기능 단위 컴포넌트로 분리했다.
- **결과:** 페이지는 데이터 조회와 화면 조합에 집중하고, 공통 UI 변경은 해당 컴포넌트에서 관리할 수 있게 됐다.

## 2. 로딩·빈 결과·에러 상태를 서로 다른 화면 상태로 다룬다

- **배경:** 데이터를 가져오는 중인 상태와 데이터가 없는 상태, 요청이 실패한 상태가 비슷한 문구와 개별 마크업으로 표시됐다.
- **결정:** 페이지 또는 섹션 전체 상태는 `StateSection`, 목록 안의 작은 안내는 `StateMessage`로 구분한다.
- **결과:** 사용자가 기다려야 하는지, 결과가 없는지, 다시 시도해야 하는지 구분할 수 있고 상태 UI의 크기와 색상을 일관되게 유지한다.

## 3. 검색 입력 상태와 실제 조회 조건을 분리한다

- **배경:** 검색어 입력마다 URL query와 조회 조건이 즉시 변경되어 불필요한 상태 갱신이 발생했다.
- **결정:** 입력값은 즉시 화면에 반영하되, 실제 검색값은 `useDebouncedValue`를 거쳐 일정 시간 입력이 없을 때 변경한다.
- **보완:** 검색어를 지웠을 때 이전 타이머 값이 URL을 되돌리지 않도록 현재 입력값과 디바운스 값이 일치할 때만 query에 반영한다.
- **결과:** 입력 경험은 유지하면서 실제 조회와 URL 변경 횟수를 줄였다.

## 4. 검색과 페이지 위치는 URL로 복원한다

- **배경:** 목록 2페이지에서 상세 화면으로 이동한 뒤 돌아오면 첫 페이지로 초기화됐다.
- **결정:** 검색어와 페이지 번호를 URL query로 관리하고 상세 화면으로 이동할 때 현재 목록 경로를 함께 전달한다.
- **결과:** 새로고침하거나 상세 화면에서 목록으로 돌아와도 사용자가 보던 검색 조건과 페이지를 복원할 수 있다.

## 5. 관리자 권한과 콘텐츠 유형을 데이터로 표현한다

- **배경:** 특정 닉네임을 관리자처럼 취급하면 이름 변경에 취약하고 API를 직접 호출했을 때 공지 등록을 막을 수 없다.
- **결정:** 사용자 권한은 `users.role`, 콘텐츠 유형은 `posts.post_type`으로 저장한다. 프론트엔드는 권한에 따라 공지 작성 UI를 노출하고, 백엔드는 공지 생성·수정 요청에서 관리자 권한을 다시 검증한다.
- **결과:** 화면 노출과 실제 권한 검증을 분리하고 일반 게시글과 공지를 같은 게시글 구조 안에서 관리한다.

## 6. 공지는 정보 밀도를 유지하는 얇은 티커로 제공한다

- **배경:** 게시판의 중심 경험을 가리지 않으면서 관리자가 작성한 공지를 첫 화면에서 발견할 수 있어야 했다.
- **결정:** 공지는 헤더 아래의 얇은 티커로 노출하고 선택하면 해당 게시글 상세로 이동한다. 공지가 하나일 때는 반복하지 않고, 여러 개일 때만 순환한다.
- **접근성:** 사용자가 움직임 감소를 설정한 경우 `prefers-reduced-motion`에 따라 애니메이션을 줄인다.

## 7. 외부 폰트는 파일이 아니라 사용 정보와 웹폰트 경로를 다룬다

- **배경:** 추천 대상 폰트의 파일을 직접 저장하거나 재배포하면 폰트별 라이선스와 배포 조건을 별도로 검토해야 한다.
- **결정:** 폰트 파일 자체는 저장·재배포하지 않고 출처, 라이선스, 웹폰트 URL 등 추천과 표시를 위한 메타데이터를 관리한다.
- **결과:** 원 배포처를 안내하면서 웹폰트가 제공되는 범위 안에서 미리보기에 적용한다.

## 8. 독립적인 변환 로직부터 단위 테스트한다

- **배경:** 모든 화면 흐름을 한 번에 자동화하기보다 입력과 출력이 분명하고 회귀 가능성이 있는 로직부터 검증할 필요가 있었다.
- **결정:** Vite 기반 프로젝트와 설정을 공유하기 쉬운 Vitest를 사용하고, 디바운스 훅, 날짜 포맷, 추천 데이터 정규화를 우선 테스트한다.
- **결과:** 시간 지연 처리와 데이터 변환 규칙을 UI 수동 확인에만 의존하지 않고 반복 검증할 수 있다.
